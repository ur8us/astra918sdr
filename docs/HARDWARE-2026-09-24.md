## DSP failure and correction

The initial image fell behind the 240 ksps DMA capture stream. A 512-output
sample block has a 4267 us budget; measured polling intervals reached 7438 us,
and the bounded ring correctly stopped capture on overrun. Borrowing filter
coefficients instead of copying arrays reduced that interval to 5550 us but
was still insufficient.

The corrected convolution uses mirrored history buffers and symmetric tap
pairs (conjugate symmetry for the SSB filter). This halves multiplications and
removes per-tap ring wrapping while preserving the filter lengths and design.
Core 1 has a 64 KiB stack for the larger filter state. RTT reports aggregate
block processing time every 1024 blocks.

An initial 30-second run measured 2938–2940 us mean per block, with a maximum
3776 us during startup, and no capture fault. These are initial measurements,
not a completed simultaneous I/Q/audio endurance qualification.

All 53 host tests and seven cross-process acceptance tests pass. A new broadband
test compares paired convolution with a full-convolution oracle in both
sidebands at −45/0/+45 kHz; results differ by at most one PCM count. External
WSJT-X decoders still decode FT8, FT4 and WSPR after the production DSP in
USB/+45 kHz and LSB/−45 kHz software tests.

## Vendor access and application fixes

After the user installed `packaging/70-astra918.rules`, an SWD reset caused USB
re-enumeration and applied the access ACL. Both the receiver and Picoprobe are
accessible without root. The vendor client claims interface 4 only.

The direct 30-second audio/CAT/IQ test passed at 120002.95 complex samples/s
(7052 frames), with contiguous sequences and sample indices and no new fault
counters. Signed offsets −45/0/+45 kHz, USB/LSB, CAT/vendor tuning in both
directions, antenna selections, gain modes, filter width, capacitor and rejected
out-of-bounds offset passed. The deliberate unread-I/Q test stopped only I/Q,
incrementing its drop/USB counters; audio recording and CAT continued. Explicit
Stop also left audio/CAT working. Evidence: `artifacts/hardware-controls-2/`.

Physical SDR++ use exposed three issues, corrected in source commit `e5a573a`:

* A partial old USB frame survived a previous stalled owner. Start now stops
  and drains I/Q before resetting its parser and starting a new generation.
* Reconfiguration commands could starve I/Q reads in the shared control thread.
  A separate reader now consumes I/Q while the control owner applies settings.
* Recentring during a held VFO drag made the same cursor position repeatedly
  retune. The linked VFO now commits a mouse gesture on release.

Regression tests cover stale bytes and mouse-release behavior. Seven offline
acceptance tests, Linux CTest, ASan/UBSan portable-client and real-module
lifecycle tests pass. Windows portable-client cross-build and protocol/simulator
tests under Wine pass. Native Windows/macOS USB and module testing remain unrun.

On the physical receiver, a released VFO drag changed 14.074 to 14.080 MHz once;
WSJT-X followed. Selecting 40 m in WSJT-X retuned SDR++ to 7.074 MHz. Editing the
offset to +45 kHz preserved that dial, and the subsequent WSJT-X 20 m selection
preserved the offset. Stop/start retained working reception. All observations
use an isolated SDR++ profile and the actual hardware, without simulator input.

The cumulative pre-fix and intentional-fault baseline is two I/Q drops and

## Helpers and scope

The receive-only helpers are `scripts/test_hardware.py` (explicit serial,
audio/CAT/IQ and optional reversible control/stall checks) and
`scripts/live_hardware_wsjtx.py` (isolated physical WSJT-X profile). Neither
helper flashes firmware or saves receiver settings.

After installing `packaging/70-astra918.rules` and reloading/retriggering udev,
close WSJT-X and other receiver controllers before running the direct test:

```sh
python3 scripts/test_hardware.py --serial C1E27EA41B7ECCC3 \
  --seconds 30 --controls --stall --output artifacts/hardware-controls
python3 scripts/test_hardware.py --serial C1E27EA41B7ECCC3 \
  --seconds 1800 --output artifacts/hardware-endurance
```

The direct test measures hardware transport independently of the applications;
it does not replace the separate simultaneous WSJT-X/SDR++ application test.
It records raw audio, per-second state and summary JSON in the chosen folder.
The 30-second control/stall helper has run successfully as recorded above.
The example 1800-second direct test has not run. Generator testing and calibrated
RF measurements are excluded entirely.

`scripts/test_hardware_persistence.py` is separate because it explicitly saves
settings and resets the MCU. Its optional `--torn-commit` models an interrupted
write by removing the newest record's commit page, with SWD backups and byte-for-
byte verification that no other settings bytes changed. It is not a physical
power-cut-during-write test.
