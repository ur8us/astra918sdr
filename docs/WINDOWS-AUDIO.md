# Windows first-connection audio plan

Status: proposed; no implementation, flashing or Windows hardware validation
was performed for this plan. Initial target is Windows 11 and Windows 10 x64;
confirm the affected Windows version and driver history during diagnosis.

## Required result

On a normal Windows installation that has never seen this receiver, connecting
it for the first time must automatically create an enabled recording endpoint
for Astra918, a CAT COM port, and a vendor interface usable by the GUI or SDR++.
The recording endpoint must appear in Windows Sound input devices and the
WSJT-X input selector. No Astra918 installer, Zadig, custom INF, registry edit,
administrator action, or manual enabling of hidden audio endpoints is required.
First connection must also work without internet access using Windows inbox
drivers. Automatic visibility does not mean forcing the receiver to become the
user's system-default recording device.

## Evidence and unresolved cause

The source currently builds USB Audio Class 1 mono, 16-bit, 12 kHz capture.
`firmware/src/usb_audio.rs` already declares input terminal type 0x0603 (Line
Connector), and `firmware/tests/usb_descriptors.rs` asserts that value. It does
not currently declare type 0x0710 (Radio Receiver).

Microsoft documents that Radio Receiver endpoints are normally created
disabled and hidden. Line Connector is explicitly exempt from this LineLevel
policy. This makes terminal classification an important check, but it does not
establish the cause of the reported failure: the descriptor actually returned
by the affected receiver and the Windows device state are still unknown.
[Microsoft endpoint enablement policy](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/pkey-audiodevice-enableendpointbydefault).

The device class/subclass/protocol are already EF/02/01, with audio on interfaces
0/1, CDC ACM on 2/3, and vendor control/IQ on 4. The vendor function already
declares Microsoft OS 2.0 WINUSB compatibility and a device interface GUID.
Existing physical qualification is Linux-only; Wine and cross-compilation do
not establish Windows USB/audio behavior.

## Implementation sequence

1. **Identify the failing layer on native Windows.**
   Record the Windows version, receiver serial, installed firmware identity,
   and any previous Zadig/custom-driver use. Capture the actual device,
   configuration, BOS and Microsoft OS descriptors using USBView or equivalent
   diagnostics. Collect the relevant SetupAPI installation log and PnP parent
   and child driver bindings. Enumerate recording endpoints including active,
   disabled, unplugged and not-present states through the Windows MMDevice API.
   Distinguish failure to enumerate USB, failure to load the audio driver,
   creation of a hidden/disabled endpoint, and application-only capture failure.
   First reproduce without changing drivers or manually enabling the endpoint.

2. **Correct the firmware only where the evidence requires it.**
   Verify the flashed image advertises the intended Line Connector terminal,
   connected to the USB streaming output terminal. Keep this classification
   for radio audio; it describes how Windows presents the stream, not an added
   physical connector. Audit AudioControl total lengths, terminal links,
   streaming alternate settings, PCM format, isochronous endpoint descriptors,
   and advertised class requests against the actual generated bytes.
   Ensure the audio IAD groups only interfaces 0/1 and CDC groups only 2/3.
   Give the audio function a clear Astra918 name using appropriate USB strings
   and verify its resulting Windows display name. Explicitly set a release
   revision for descriptor changes and record artifact hashes; retain the
   stable serial and interface numbering. Do not assume changing bcdDevice
   clears existing Windows endpoint state.

3. **Verify automatic binding of all three functions.**
   The parent must use the Windows composite driver, the audio child the inbox
   USB audio driver, and CAT the inbox CDC serial driver. Check that the
   Microsoft OS descriptor function subset targets interface 4 only and that
   its WINUSB ID and DeviceInterfaceGUIDs are delivered correctly. Correct any
   binding defects without supplying a whole-device WinUSB installer. Remove
   routine manual driver installation from the Windows setup instructions once
   automatic binding is qualified. Document recovery from an old incorrect
   driver binding separately from clean first-connection behavior.
   [USB audio automatic loading](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/usb-audio-class-system-driver--usbaudio-sys-),
   [IAD requirements](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/usb-interface-association-descriptor),
   [WinUSB automatic installation](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/automatic-installation-of-winusb),
   [CDC serial automatic installation](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/usb-driver-installation-based-on-compatible-ids).

4. **Verify usable capture after visibility is fixed.**
   Retain the existing 12 kHz USB stream initially. Confirm Windows can open it
   and that the audio path selected by WSJT-X handles its 48 kHz capture request.
   Treat unsupported capture format and application microphone permissions as
   distinct from missing endpoint enumeration. If native Windows measurements
   show the 12 kHz format prevents reliable application capture, evaluate an
   actual 48 kHz firmware output path with interpolation, correct packet sizes,
   clock-drift handling, and RP2350 CPU/USB budget checks. Do not simply advertise
   48 kHz while sending 12 kHz samples. That larger change is conditional, not
   the initial fix for a missing recording endpoint.

5. **Add focused diagnostics and regression coverage.**
   Extend the existing descriptor test to assert complete audio/CDC IAD grouping,
   terminal topology and names, and the exact interface-4 scope of the WinUSB
   descriptor. Add a read-only Windows diagnostic command that reports device
   identity, driver binding, recording endpoint state, supported capture formats,
   and capture-open errors. It must work for diagnosis even if vendor WinUSB
   binding is broken. Include clear guidance for disabled endpoints, wrong
   bindings and application permissions without modifying Windows settings.
   Build both RP2350 variants and the Windows host programs, and perform focused
   Linux/macOS compatibility checks for any changed USB descriptors.

6. **Qualify the actual first-connection experience and package the result.**
   Use native Windows 11 and Windows 10 x64 installations with no previous
   receiver identity or driver package. A clean Windows image on physical
   hardware is preferred; unplugging a previously installed device is not a
   clean first-connection test. Keep the PC offline for the initial insertion.
   Separately test upgrade behavior on a PC that previously saw the receiver,
   including any previously hidden endpoint or incorrect driver binding.
   Publish the qualified UF2, hashes, Windows diagnostics and short setup guide.
   Keep fresh-install results separate from recovery results. No RF generator
   is needed or used.

## Acceptance checks

- First insertion automatically loads all three function drivers without a
  user-supplied driver package, administrator action or internet access.
- An enabled Astra918 recording endpoint appears in ordinary Windows Sound
  input settings and WSJT-X; hidden-device display and manual enabling are
  unnecessary. Its Windows MMDevice state is ACTIVE.
- WSJT-X records receiver audio and CAT tuning works while SDR++ streams 120 ksps
  IQ. Repeat with the GUI as the vendor controller instead of SDR++.
- Reconnect, reboot and sleep/resume preserve usable audio/CAT/vendor access.
  Stopping or disconnecting SDR++ does not remove or reset audio or CAT.
- No unexpected driver binding appears on the composite parent or audio/CDC
  functions. Saved receiver settings survive the firmware upgrade.
- Results name the exact Windows builds, firmware hashes and connection paths
  tested. Cross-build success alone is not marked as Windows hardware success.

The first implementation milestone is the native Windows diagnostic capture and
a confirmed cause. The second is the smallest firmware correction, if needed,
with a clean first-connection pass. Application-format improvements and broader
Windows packaging follow only where those results demonstrate a need.
