## Changes

Both applications use a capacitor slider bounded to 0-4095, including direct
numeric entry. Values apply during motion, coalesced to at most ten updates
per second during a drag, with a final update on release. The SDR++ range label
uses ASCII and neither application has a capacitor Apply button.

SDR++ left-right tuning now moves the linked audio/CAT channel within a fixed
RF spectrum. Center/aim tuning sets offset zero and tunes the RF center with
the channel. Firmware commands 38/39 apply these changes atomically; channel
tuning restarts the DSP epoch without changing the CMX918 PLL. Complete audio
passband validation and a 500 Hz guard limit movement at the spectrum edges.
CAT, GUI dial edits and the source panel's Tune button retain their existing
offset-preserving behavior.

Release builds omit the simulator controls. The GUI also omits `--simulator`
from its release CLI, and ignores old simulator preferences. SDR++ release
modules ignore the simulator environment variable; the launcher rejects an
explicit simulator request unless a Debug module was selected. Developer
simulator tests remain available.

The GUI discovers USB receivers on startup and connects once if exactly one
device with a readable serial is found. Multiple/zero devices require selection;
disconnect does not trigger automatic reconnection. Connection always adopts
the receiver's existing state.

## Physical checks

The RP2350A image was flashed through Picoprobe with verification. The previous
runtime configuration was recorded and restored, including the user's manual
RF and IF gain selections. Both settings sectors were read before and after
testing and matched exactly: these operations did not save settings.

An isolated release GUI connected automatically to the sole receiver without
clicking Refresh or Connect. While the slider was held, its applied readback
advanced to code 3100 (185.4 pF). Direct entry of 5000 clamped to 4095, and -123
clamped to zero. The release window had no simulator control.

In SDR++, a held slider applied code 3180 (190.2 pF); numeric entry likewise
clamped to both endpoints. The label displayed `0-4095` correctly. While actual
I/Q and WSJT-X audio/CAT were running:

* A left-right drag changed dial 14.074000 to 14.083500 MHz, offset 9500 Hz,
  while the spectrum center stayed 14.074000 MHz.
* Selecting center/aim retained dial 14.083500 MHz and made it the RF center,
  with offset zero. Clicking farther along the spectrum retuned both to
  14.098500 MHz.
* Back in left-right mode, a one-hertz wheel change in the main frequency
  display produced dial 14.098501 MHz, offset 1 Hz, RF center 14.098500 MHz.
* WSJT-X's physical CAT readbacks followed the changed dial. All I/Q drop,
  capture, USB and audio fault counters remained zero during these UI checks.

The extended direct control test exercised both sidebands at channel offsets
-45049/0/+45049 Hz, verifying fixed center and CAT readback, plus center tuning
and rejection outside the passband. A 30-second stream measured 120001.74
complex samples/s across 7049 contiguous frames, with zero new faults.
The deliberate I/Q stall then incremented its expected drop/USB counters once;
audio capture and CAT continued. Runtime settings were restored afterward.

Direct ALSA capture initially failed because PipeWire owned the receiver device.
The helper now records that failure without masking it during cleanup, and
supports an explicit `--audio-backend pipewire` using the serial-specific
physical source. That backend passed the final test and recorded 403556 mono
12 kHz audio samples. No default audio route or normal WSJT-X profile changed.

## Software checks and limits

54 shared host/USB tests, two GUI tests and all seven cross-process acceptance
tests pass. The real SDR++ module lifecycle test covers normal tuning, spectrum
limits, switching to center mode without changing the dial, center retuning,
secondary VFO isolation and CAT synchronization. It also passes ASan/UBSan.
Rust formatting, host/ARM/GUI Clippy, both RP2350 builds, Linux module/GUI builds
and Windows portable-library/GUI cross-builds pass. The release GUI CLI under
Wine has no simulator option; the debug Linux GUI connects to the simulator.

Native Windows/macOS hardware and module loading are not claimed. These are
functional control and transport tests, not calibrated RF measurements or a
new long-duration endurance qualification. No physical cold-start test was
performed during this update.
